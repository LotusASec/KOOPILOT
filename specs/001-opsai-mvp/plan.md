## Summary

**Primary Requirement**: Build an end-to-end AI-powered WhatsApp operations assistant for e-commerce that classifies customer intent, looks up order/stock data, generates AI responses, and requires human approval before sending.

**Technical Approach**: 
- 4 FastAPI microservices (API Gateway, AI Service, Order Service, Stock Service) communicating via REST/JSON
- PostgreSQL single database with 4 entities (customers, orders, stock, conversations)
- Gemini API for intent classification (temperature 0.3) and response generation
- Simple web UI for human approval of AI-generated responses
- Synchronous request-response flow, no queues or background workers
- Local development environment; demo-ready, not production-ready

## Technical Context

**Language/Version**: Python 3.11+  
**Primary Dependencies**: FastAPI 0.104+, Pydantic 2.0+, psycopg2-binary (PostgreSQL adapter), google-generativeai (Gemini SDK), uvicorn (ASGI server)  
**Storage**: PostgreSQL 13+ (single instance, local or Docker)  
**Testing**: pytest for unit/integration tests, requests for API testing  
**Target Platform**: Linux server (local dev or VM), single-instance deployment  
**Project Type**: Web service (REST API + microservices + web UI)  
**Performance Goals**: End-to-end message processing < 5 seconds; approval cycle < 2 minutes per message  
**Constraints**: 
- Max 4 backend services (no more)
- Synchronous request-response only (no async workers, no queues)
- REST-only APIs (no GraphQL, gRPC, or WebSockets)
- No caching layer (direct PostgreSQL queries)
- Deterministic AI responses (Gemini temperature 0.3)

**Scale/Scope**: 
- 5-person team, 8 hours per person max (48 hours total for hackathon)
- Demo scope: handle 5–10 mock customer messages end-to-end
- No production scalability required

## Phase 0: Research & Unknowns Resolution

**Status**: Ready to Execute  
**Outputs**: `research.md`

### Known Unknowns

All technical decisions have been clarified by the specification and constitution. Key decisions documented:

1. **Gemini API Implementation**
   - Decision: Use google-generativeai SDK with temperature 0.3
   - Rationale: Low variance for deterministic demo behavior
   - Alternatives considered: Direct REST calls (more verbose), other LLM APIs (not specified in constraints)

2. **PostgreSQL Schema Design**
   - Decision: 4 tables (customers, orders, stock, conversations) with normalized structure
   - Rationale: Simple for hackathon, prevents data inconsistency, fast indexed queries
   - Alternatives considered: Denormalized schema (harder to maintain), NoSQL (violates architecture rule)

3. **Microservices Communication**
   - Decision: Synchronous REST calls with timeouts (10-second for external APIs, 5-second for internal)
   - Rationale: Simpler debugging, easier demo walkthrough, no infrastructure overhead
   - Alternatives considered: Message queues (adds complexity), async/await (risk of timeout bugs)

4. **Web UI for Approval**
   - Decision: Simple HTML + vanilla JS, no framework (React, Vue, etc.)
   - Rationale: Hackathon time constraint; vanilla JS sufficient for single approval flow
   - Alternatives considered: Full-stack framework (overkill for demo), CLI-only (less impressive for demo)

5. **Authentication & Security**
   - Decision: API keys in .env only; no JWT, OAuth, or RBAC
   - Rationale: Hackathon environment, demo runs on localhost/internal network only
   - Alternatives considered: Full auth (8+ hours to implement), hardcoded secrets (bad practice)

6. **Testing Strategy**
   - Decision: Unit tests for business logic (Gemini client, models), integration tests for service communication
   - Rationale: Ensure AI classification works reliably, services talk to each other correctly
   - Alternatives considered: Full E2E tests only (hard to mock), no tests (risky for demo)

- ✅ All technology choices confirmed and documented

- ✅ REST API contracts defined (see Phase 1: contracts/)
- ✅ Best practices applied: stateless services, contract-first APIs, human-in-the-loop, synchronous request-response
